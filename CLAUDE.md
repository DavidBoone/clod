# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A Docker image for running Claude Code or Codex in ephemeral containers, plus the `clod` launcher (bash, kept compatible with the bash 3.2 macOS ships). Supported hosts: macOS (Colima or Docker Desktop) and Linux (rootful Docker Engine). No compose, no persistent containers - just `docker run` with `--rm`.

## Build & Run

```bash
clod          # launcher script; builds images as needed and wraps docker run
```

`Dockerfile` is the generic base image (`clod`). Personal or per-stack tooling goes in variants: `~/.clod/images/<name>/Dockerfile` or, failing that, a bundled `images/<name>/Dockerfile` in this repo, built `FROM clod` (or another variant), selected with `CLOD_IMAGE=<name>` and auto-built as `clod-<name>` when its files or the image it is `FROM` change. Variants combine as `CLOD_IMAGE=a+b`: clod builds `clod-a`, then `b` with `--build-arg BASE=clod-a` as `clod-a.b`, in the order given, so every bundled variant starts `ARG BASE=clod` / `FROM $BASE` (as does `clod image new`'s starter), and clod expands ARG defaults in `FROM` lines to find what a variant builds on. A variant can also be `FROM clod-a.b`, which `clod image new NAME a+b` starts. Bundled variants are examples for a language or stack; keep them generic. A variant's instructions for Claude go in a Markdown file it copies into `/etc/clod/.claude/rules/` (the bundled ones use a `CLAUDE.md` beside the `Dockerfile`); the entrypoint loads `/etc/clod` with `--add-dir=/etc/clod` and `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`. The base image's own instructions, describing the container to Claude, are `container.md`, copied in as `/etc/clod/.claude/rules/clod.md`. The launcher builds the base from its own (symlink-resolved) directory when `Dockerfile`, `entrypoint.sh` or `container.md` change.

The `clod` launcher mounts a home from `~/.clod/homes/<name>` (or any host path, or with `vol:<name>` the Docker volume `clod-home-<name>`, which Docker fills from the image's `/home/claude`) at `/home/claude` and `.` at `/workspace`, or with `-w` another directory or, as `vol:<name>`, the Docker volume `clod-workspace-<name>` (an option only, never a setting; the `.envrc` is looked up from the workspace, and a volume workspace reads none). Each home keeps its own Claude login (MCP OAuth tokens live in the same file). `~/.clod/shared` is mounted read-only at `/etc/claude-code` (managed settings and CLAUDE.md for every home); until the user creates it (`clod shared new` copies the starter), the repo's `shared/` is mounted there instead. `shared/` is the default set: a statusline with the managed settings enabling it, and no `CLAUDE.md`, so a user's `~/.clod/shared/CLAUDE.md` holds only their own instructions (`clod shared new` points out one that still repeats `container.md`). Keep it generic; personal instructions belong in the user's own `~/.clod/shared`. Launcher settings (`CLOD_HOME`, `CLOD_IMAGE`, `CLOD_PORTS`, and `CLOD_COMMAND` for what a bare `clod` runs) come from options (`-H`, `-i`, `-P`) or else the host shell environment; container variables come from the nearest direnv-allowed `.envrc` up the tree (only that one file). Launcher settings set by that file are defaults for the shell's, never container variables, and `~/.clod/config` (edited by `clod default KEY VALUE`, with `--reset` to remove one) holds defaults for both. `CLOD_PORTS` publishes ports (host:container) on the host's 127.0.0.1. `--docker` mounts the Docker socket (`/var/run/docker.sock`, the same path on Linux, in Colima's VM and in Docker Desktop's) with `--group-add` of its gid as a throwaway container sees it, and passes the project's host path as `CLOD_HOST_WORKSPACE` (none for a volume or scratch workspace); it fails if Docker isn't local. It is deliberately an option only, never a `CLOD_*` setting, so no `.envrc` or config can turn it on. `--scratch` mounts an empty anonymous volume at `/workspace` instead of `.` (the base image makes `/workspace` claude's, which the volume copies), sets `CLOD_SCRATCH`, reads no `.envrc` and skips the workspace refusal; it is an error with `-w`. The bundled `docker` variant supplies the CLI and tells Claude how sibling containers behave. `clod image build [NAME...]` builds the stale images in the chains of the named images (or with none, the current image) without starting a container, `clod image rebuild [NAME...]` rebuilds the whole chains without cache, each image once, pulling a fresh base, and `--skip-build` runs an existing image without checking it; images replaced by any build are pruned. Claude Code and Codex install themselves into the home on first run and self-update. The launcher refuses to mount `$HOME`, a directory above it, `~/.clod` or anything under `~/.clod/homes` as a directory workspace, and `$HOME`, a directory above it, `~/.clod` or `~/.clod/homes` itself as the container home, unless run with `--force`. It checks Docker is reachable before building. `-i clod-NAME` means variant `NAME`, and `-i clod-a.b` the combination `a+b`. The base Dockerfile avoids BuildKit-only syntax, since Homebrew's docker has no buildx and builds with the classic builder; CI checks this.

The command line is strict (`clod --help`): clod's options come before the command, unknown options and commands are errors, as are arguments a command doesn't take, and a command's arguments go after it; with no command the default command (`CLOD_COMMAND`, `claude` unless set) runs, and `--` passes the rest to it. The launcher always passes the command to the entrypoint as its first argument. Options only change how a run works; anything that does something else and exits is a command. Commands that manage something are a singular noun, matching its option (`-i`, `-H`, `-w`), with a verb; the bare noun lists (`shared` takes a verb):

- `image` lists the base, the bundled variants, the user's and the images clod built, marking those stale or `in use` (a container uses them); `image show NAME` shows how NAME is built; `image new NAME [FROM]`; `image build [NAME...]` and `image rebuild [NAME...]` (above); `image rm [NAME...]` removes only images clod built, by their `-i` names, or with none the image `-i`/`CLOD_IMAGE` selects (an image others are built on loses only its name); `image prune` removes the stale images clod built, keeping those in use
- `home` lists the homes and their logins; `home rm vol:NAME...` removes volume homes only (directory homes are folders the user deletes)
- `workspace` lists the volume workspaces, marking those a container uses; `workspace rm NAME...` removes them, named `NAME` or `vol:NAME`
- `shared new` creates `~/.clod/shared` from the starter, or if it exists lists the starter's files it lacks or differs on (`--force` replaces it, keeping a backup); `shared diff` shows the diff between the starter and `~/.clod/shared`
- top-level: `env`, `default`, `update` (git pull in clod's checkout, fast-forward only), `install` (links clod onto PATH) and `completion` (prints a tab-completion shim for bash and zsh)

`home rm` and `workspace rm` delete the only copy of their files: in a terminal they list what they'll delete and ask y/N, and `--force` skips the question and is required without a terminal; Docker refuses to remove a volume a container uses. `clod build` and `clod rebuild` are hidden, deprecated aliases of `image build` and `image rebuild`: they print a note naming the new form and are left out of `--help`, the docs and completion.

The shim calls the hidden `clod __complete WORDS...`, which exits 1 where a file name belongs (a run command's arguments, a home path, `install`'s directory) so the shell completes files there and nowhere else. It completes every noun's verbs and their arguments: image names after `image show`, `rm`, `build` and `rebuild`, `vol:NAME` homes after `home rm`, volume workspace names after `workspace rm`, and `new` and `diff` after `shared`. It reads the `commands`, `options` and `settings` lists, the nouns' verb lists and the variant and home directories, never the `.envrc`, and Docker only for volume homes and workspaces and `image rm`'s built images, so a new command, verb, option or setting needs adding to those lists to complete.

On a Linux host, where bind mounts keep host ownership, the launcher builds the base image with `--build-arg CLOD_UID/CLOD_GID` set to the host user's ids (folded into the build hash) so `claude` owns its files, and maps `host.docker.internal` to the host gateway. On macOS the VM's file sharing handles ownership, so `claude` keeps uid 1000.

## Tests

`test/run.sh` is the test suite: shellcheck (`lint`), the launcher's behaviour end to end (`base`), builds without BuildKit (`classic`), and each bundled variant (`variant-NAME`; `go+sudo` covers go and sudo, and `docker-socket` the docker variant). CI runs a few of them per job on fresh GitHub runners, the quick variants together, since every job builds the base image first. It needs Linux and a Docker it can have to itself, since it builds, replaces and prunes the clod images and mounts the socket into containers, so outside CI it runs only on a throwaway VM, with `--yes`; `test/run.sh lint` runs anywhere. Each run gets a fresh `HOME`. `test/tab-complete.py` types command lines into real bash and zsh through a pty, for the completion cases that depend on how each shell splits words. A new feature gets a `test_*` function in its group's list.

## Security

The container defines what the agent can reach; within it, the agent runs unrestricted:

- Claude Code runs with `--dangerously-skip-permissions` unless its arguments choose a permission mode, and Codex with `--dangerously-bypass-approvals-and-sandbox`
- The workspace and the whole container home (`~/.clod/homes/<name>`, not the user's own home) are mounted read-write. A new home starts empty and holds only what the user gives it (logins made in the container, copied keys), and all of that is visible to the agent; so are the variables passed in from the `.envrc`
- The container has normal outbound network access and can reach host services via `host.docker.internal`
- With `--docker`, the agent has the Docker socket, which is root on the Docker host (on macOS, the VM, which mounts the user's home folder): it removes the boundary entirely
- Claude Code installs via `curl https://claude.ai/install.sh | bash` on first run
- `--rm` discards everything outside the home and workspace mounts after each run

## Docs

`README.md` is the front page: install, first run, and how clod works and what the agent can reach, short enough to read in one go. Everything else is a page in `docs/` linked from its "More" list: `usage.md`, `images.md`, `configuration.md`, `shared-config.md`, `docker-socket.md` (`--docker` and what it gives away), `security.md`, `docker.md` (installing Docker, Linux host notes) and `without-clod.md`. A new feature's docs go in the page it belongs to, not the README. `container.md` is the agent's view: what it can see in the container, how the user changes clod on the host, and links to these pages on GitHub; keep it in step with them.

`docs/statusline.svg`, shown in `docs/shared-config.md`, is rendered from the real statusline by `docs/statusline-svg.sh > docs/statusline.svg`: it runs `shared/statusline.sh` on sample input and converts the 16-colour output with `docs/ansi2svg.py`. Regenerate it when the statusline's look changes.
